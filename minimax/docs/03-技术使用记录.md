### 1.2 模型在流程中的位置

```
业务工程 ──ingest──> seekdb ──retrieve──> 开发上下文 ──prompt──> MiniMax
```

## 二、数据库查询记录（seekdb / OceanBase）

### 2.1 接入方式

| 项 | 值 |
| --- | --- |
| 产品 | OceanBase seekdb 1.4.0（嵌入式实例，通过 `pylibseekdb` 1.4.0.post2 启动） |
| 引擎版本串 | `5.7.25-OceanBase seekdb-v1.4.0.0` |
| 协议 | MySQL 协议（Unix Domain Socket），客户端 `PyMySQL` |
| 库名 | `sdctx` |
| 代码 | `sdctx/seekdb_store.py`（`SDCTX_SEEKDB_MODE=server` 时可切换到外部 seekdb / OceanBase） |

### 2.2 数据库中真实保存的内容

| 表 | 内容 | 行数（一次完整导入后） |
| --- | --- | --- |
| `ctx_document` | 每个规格 / 代码 / 测试文件的整份原文 | 8 |
| `ctx_spec_item` | 每个可独立检索的规格条目（R-xxx-xxx） | 13（规格 v1）/ 14（升级到 v2 后） |
| `ctx_code_symbol` | 用 `ast` 解析出的类 / 函数符号及行号 | 63 |
| `ctx_test_case` | 每个测试函数 | 92 |

四张表都建了 **ngram 全文索引**（`FULLTEXT INDEX ... WITH PARSER ngram`），
中文规格可以直接被 `MATCH ... AGAINST` 命中。

### 2.3 查询确实参与了上下文构造

检索由 `sdctx/retrieve.py` 执行，两路都在数据库里完成：

1. **全文检索**：`MATCH(title, content) AGAINST (<任务描述> IN BOOLEAN MODE)`；
2. **词项加权命中**：把任务描述拆成词项（英文标识符 + 中文二元组），
   在数据库里用 `CASE WHEN ... LIKE ... THEN n END` 累加打分。

两路结果按 id 合并排序，取 top-k。**最终进入上下文的规格条目、代码符号、测试用例，
全部来自这两条 SQL 的返回行**，没有在 Python 侧做二次"凭印象挑选"。

原始 SQL 与返回行见 `evidence/04-seekdb-查询记录.txt`，例如：

```sql
SELECT spec_path, item_id, title, version
FROM ctx_spec_item WHERE spec_path LIKE '%SPEC-003%' ORDER BY item_id;
```

```sql
SELECT path, qualified_name, start_line, end_line
FROM ctx_code_symbol WHERE qualified_name LIKE 'Scheduler.%' ORDER BY start_line;
```

### 2.4 规格升级后数据库内容确实变了

升级 SPEC-003 到 v2 并重新 `ingest` 之后：

| 时刻 | `ctx_spec_item` 中 SPEC-003 的条目 | version |
| --- | --- | --- |
| 升级前 | R-003-001、R-003-002、R-003-003、R-003-004 | `v1` |
| 升级后 | R-003-001、R-003-002、R-003-003、R-003-004、**R-003-005** | `v2` |

对照证据：`evidence/03-上下文输出-规格v1.json` 与 `evidence/10-上下文输出-规格v2.json`
的 `specs[].item_id` / `specs[].version` / `specs[].content`。

## 三、PowerContext 状态写入与复用记录

### 3.1 接入方式

| 项 | 值 |
| --- | --- |
| 产品 | PowerContext 1.4.1（OceanBase 开源的 AI Agent 上下文服务） |
| 部署 | 本地 Server，`http://127.0.0.1:18080`，SQLite 后端 |
| 客户端 | `sdctx/powercontext_client.py`（标准库 `urllib`）+ `sdctx/state.py` |
| Scope | 一个 Scope 隔离本次作品的任务状态，id 由 `sdctx init` 创建并缓存到 `.sdctx/scope_id` |
| 用到的接口 | `POST /v1/scopes`、`POST /v1/sources/content`、`GET /v1/scopes/{id}/sources/content/{source_id}`、`POST /v1/memory/remember`、`POST /v1/memory/search` |

### 3.2 状态是怎么存的

一次任务状态被拆成两层写入 PowerContext：

| 层 | 写入接口 | 内容 | 读取接口 |
| --- | --- | --- | --- |
| **Source 日志** | `POST /v1/sources/content`，`source_id = sdctx-state-<task_id>-r<N>` | 完整 JSON 状态：任务、上下文（规格 / 代码 / 测试）、进度、验证结果 | `GET /v1/scopes/{scope_id}/sources/content/{source_id}` |
| **Atomic Memory** | `POST /v1/memory/remember`（`kind=progress`） | 一行可检索的进展摘要，形如 `SDCTX-STATE <task_id> \| status=... \| specs=8 \| code=8 \| tests=8 \| done=... \| todo=...` | `POST /v1/memory/search` |

> Content Source 不可覆盖，所以每次保存使用递增修订号 `r1, r2, ...`；
> 读取时顺序探测，取最新一版。

### 3.3 复用的证据

`evidence/05-powercontext-状态记录.txt` 记录了完整链路：

1. `sdctx state save` → 写入 Source `r1` 与 Memory 条目；
2. **换一个全新进程**执行 `sdctx state load --task-id <task_id>` → 读到 `source_found: true`，
   并取回完整状态（含上下文、已完成事项、待办事项、已有验证结果）；
3. `sdctx context` 在组装上下文时会自动读取这份状态，并填进上下文的
   "任务状态（来自 PowerContext）"小节；
4. 再次 `sdctx state save` → 写入 Source `r2`（内容包含阶段 1 的完成情况与验证结果），
   读回时取到最新的 `r2`。

这证明：**从空状态开始保存 → 重启模块 → 读取 → 用于后续上下文与任务处理** 的闭环成立，
而且读取只依赖 PowerContext HTTP 接口，不依赖任何本地缓存文件。

### 3.4 状态在上下文里的呈现

```json
"progress": {
  "done": ["导入规格/代码/测试到 seekdb", "检索并生成开发上下文", "MiniMax 完成 SPEC-003 v1 的代码修改"],
  "todo": ["按 SPEC-003 v2 升级规格并重新导入", "用 MiniMax 完成 v2 改动"],
  "verification": "目标测试 tests/test_spec_003_job_error_isolation.py 修改前 5 失败 / 修改后 5 通过；回归测试 92 通过",
  "status": "in_progress"
}
```

这段内容直接出现在提供给 MiniMax 的提示词里（"任务状态（来自 PowerContext）"小节），
所以模型在第二轮改动时能看到上一轮已经做到了哪一步。
