# 01 运行说明

> 目标读者：评审人员。本文件说明如何在**干净环境**中从零跑通本作品。

## 0. 环境要求

| 依赖 | 版本 | 说明 |
| --- | --- | --- |
| Python | >= 3.11（本次验证使用 3.14.3） | PowerContext 与本模块均要求 3.11+ |
| 操作系统 | macOS / Linux | 嵌入式 seekdb 提供 macOS arm64、Linux x86_64/aarch64 官方 wheel |
| PowerContext | 1.4.1 | 任务状态服务，`pip install powercontext[server,client]==1.4.1` |
| seekdb | 1.4.0（绑定 `pylibseekdb` 1.4.0.post2） | 本机嵌入式实例，**不需要**额外数据库进程 |
| MiniMax | `MiniMax-M3` | OpenAI 兼容接口，需要 `MINIMAX_API_KEY` |

无需 Docker，无需单独部署数据库。

## 1. 安装依赖

```bash
cd minimax
bash scripts/setup_env.sh            # 会在 minimax/.venv 创建虚拟环境并安装 requirements.txt
source .venv/bin/activate
```

> 如果 PyPI 访问较慢，可以设置 `PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/` 后再执行。

## 2. 启动 PowerContext（任务状态服务）

```bash
bash scripts/start_powercontext.sh        # 前台启动，监听 127.0.0.1:18080
```

另开一个终端确认：

```bash
curl --fail --silent --show-error http://127.0.0.1:18080/health/live
# {"status":"ok"}
```

PowerContext 使用 SQLite 后端（默认），数据落在 `minimax/.sdctx/powercontext/`。
不需要配置任何模型 API：`explicit Memory` 与 `Source` 日志不依赖推理模型。

## 3. 配置 MiniMax

```bash
export MINIMAX_API_KEY=replace-with-your-minimax-api-key
export MINIMAX_BASE_URL=https://api.minimax.io/v1     # 使用自建/代理网关时改成你的地址
export MINIMAX_MODEL=MiniMax-M3
```

也可以直接复制 `.env.example` 为 `.env` 后按需修改（`.env` 含凭据，请勿提交）。

## 4. 体检

```bash
python -m sdctx doctor
```

输出会分别报告：seekdb 引擎版本与各表行数、PowerContext 连通性与 Scope、MiniMax 配置状态。

## 5. 手动跑一遍完整流程

```bash
cd minimax
source .venv/bin/activate

# 5.1 初始化（建表 + 全文索引 + 创建/复用 Scope）
python -m sdctx init

# 5.2 导入业务工程的规格 / 代码 / 测试
python -m sdctx ingest

# 5.3 检索并生成开发上下文
python -m sdctx context --task "让 Scheduler.run_pending 隔离单个任务异常：失败任务调用 on_error 回调，且不影响同轮其他任务" \
    --markdown

# 5.4 保存任务状态到 PowerContext
python -m sdctx state save --task "让 Scheduler.run_pending 隔离单个任务异常：失败任务调用 on_error 回调，且不影响同轮其他任务" \
    --status in_progress --done "导入资料" --todo "用 MiniMax 完成代码修改"

# 5.5 用 MiniMax 完成代码修改（落盘前会自动跑测试，失败则回滚并把失败信息喂回模型）
export SDCTX_TEST_COMMAND="python -m pytest tests/ -q"
python -m sdctx patch --task "让 Scheduler.run_pending 隔离单个任务异常：失败任务调用 on_error 回调，且不影响同轮其他任务" \
    --out evidence/minimax-turn.json

# 5.6 换一个进程读取任务状态（模拟重启模块）
python -m sdctx state load --task-id scheduler-run-pending-on-error-fa0fdd39

# 5.7 直接查数据库
python -m sdctx sql --query "SELECT spec_path, item_id, version FROM ctx_spec_item ORDER BY spec_path, item_id"
```

## 6. 一键跑通验证样例并生成全部证据

```bash
bash scripts/run_validation.sh
```

脚本会依次执行：体检 → 复位 → 导入 → 修改前测试 → 生成上下文 → 写状态 →
MiniMax 改代码 → 修改后测试 → 规格升级并重新导入 → MiniMax 再改一次 → 全量测试 →
状态复用 → 数据库查询留档，全部产物写入 `evidence/`。

## 8. 数据位置与重置

| 内容 | 位置 |
| --- | --- |
| 嵌入式 seekdb 数据 | `minimax/.sdctx/seekdb/` |
| PowerContext 数据（SQLite） | `minimax/.sdctx/powercontext/` |
| Scope 缓存 | `minimax/.sdctx/scope_id` |
| 证据与日志 | `minimax/evidence/` |

重置：

```bash
bash scripts/reset_demo.sh     # 业务工程回到 schedule 1.2.2 原始状态 + 清空索引
rm -rf .sdctx                  # 同时清空 seekdb 与 PowerContext 数据（完全从零开始）
```

## 9. 已知限制

* 嵌入式 seekdb 的数据目录一旦被多个进程同时打开会冲突；本模块按"一次一个进程"使用。
* MiniMax-M3 的推理开销较大（一次改动的完整调用通常 25–120 秒），`MINIMAX_MAX_TOKENS`
  默认 32768；推理段耗尽额度时模型可能来不及给出补丁，此时 `patch` 会返回
  `applied=false`，可在 `evidence/*-minimax-*.json` 的 `attempts` 中看到每次尝试。
* 模型偶尔会给出与真实文件不一致的上下文行，因此本模块不依赖模型的行号，
  改用 `ast` 定位符号后再整段替换，并在落盘后立刻编译校验、跑测试。
* `sdctx patch` 的测试反馈回路依赖 `SDCTX_TEST_COMMAND`，未配置时跳过验证直接落盘。
